# 项目开发与维护指南

本文档描述本项目的个人开发流程，包括任务管理、代码提交、时间记录、测试、复盘和文档维护方式。

目标不是建立复杂的管理制度，而是在有限的业余时间内，持续产出可以运行、测试和发布的游戏版本。

---

## 1. 项目基本信息

- 项目类型：Unity 2D 俯视角生存恐怖游戏
- 开发方式：个人开发
- 开发引擎：Unity 6.5
- 主要语言：C#
- 目标平台：Windows
- 版本控制：Git + GitHub
- 任务管理：GitHub Issues + GitHub Projects
- 时间记录：Clockify
- 项目文档：Markdown

---

## 2. 开发原则

### 2.1 保持项目范围可控

当前目标是完成一个可以在 10～15 分钟内通关的游戏原型。

优先完成完整游戏流程，而不是持续增加系统和功能。

原型阶段暂时不做：

- 多人联机
- 程序生成地图
- 复杂背包系统
- 技能树
- 多结局
- 大量剧情对话
- 通用游戏框架
- 与当前里程碑无关的编辑器工具

新的想法先放入 Backlog，不立即开始实现。

### 2.2 保持 main 分支可运行

`main` 分支应尽量保持以下状态：

- 项目可以正常打开
- Console 没有阻塞运行的错误
- 主要场景可以进入 Play Mode
- 已完成功能可以正常使用
- 可以生成测试构建

高风险或较大的修改应在独立分支中完成。

### 2.3 限制同时进行的任务

GitHub Project 的 `In Progress` 同时最多保留一个任务。

遇到阻塞时，应在原 Issue 中记录问题。只有在当前任务明确暂停后，才能开始其他任务。

### 2.4 优先完成，再考虑扩展

功能的优先顺序为：

1. 可以运行
2. 可以完成基本流程
3. 可以测试
4. 结构清晰
5. 体验优化
6. 视觉和音效完善

不要在基础流程尚未完成时，提前进行大规模重构或扩展。

## 3. 工具职责

不同工具只保存自己负责的信息，避免重复维护。

| 工具            | 用途                               |
| --------------- | ---------------------------------- |
| GitHub Issues   | 记录任务、Bug、研究事项和验收标准  |
| GitHub Projects | 记录任务状态、优先级和预计时间     |
| Git             | 保存代码和文档修改历史             |
| Pull Request    | 检查和合并一组完整修改             |
| Clockify        | 记录实际投入时间                   |
| Markdown 文档   | 保存长期有效的设计、流程和技术信息 |

同一份信息不应在多个位置重复维护。

例如：

- 具体开发任务放在 Issue
- 当前任务状态放在 Project
- 实际耗时放在 Clockify
- 长期开发规则放在本文档

## 4. GitHub Project 工作流

项目看板包含以下状态：

- `Backlog`
- `Ready`
- `In Progress`
- `Testing`
- `Done`

### 4.1 Backlog

尚未安排近期开发的想法、需求和问题。

Backlog 中的内容不代表一定会实现。

### 4.2 Ready

已经明确目标、完成标准和预计时间，可以直接开始的任务。

进入 Ready 的任务应满足：

- 目标明确
- 完成标准明确
- 没有未解决的前置依赖
- 预计时间不超过 4 小时

### 4.3 In Progress

当前正在开发的任务。

同时只能存在一个 In Progress 任务。

### 4.4 Testing

功能实现已经完成，正在进行：

- Unity 编辑器测试
- 边界条件测试
- 场景集成测试
- Windows 构建测试
- 必要的试玩验证

### 4.5 Done

任务已经满足完成标准，并完成代码提交或 PR 合并。

## 5. Project 字段

### 5.1 Status

表示任务当前状态：

- `Backlog`
- `Ready`
- `In Progress`
- `Testing`
- `Done`

### 5.2 Priority

表示任务优先级：

- `High`：阻塞当前里程碑，或必须优先处理
- `Medium`：属于当前阶段，但不会立即阻塞
- `Low`：可以延后处理

优先级不表示任务规模。

### 5.3 Estimate

记录任务预计需要的小时数。

推荐使用：

- `0.5`
- `1`
- `2`
- `4`

超过 4 小时的任务应继续拆分。

实际耗时不记录在 Estimate 中，实际时间统一使用 Clockify。

## 6. Issue 使用规范

### 6.1 什么情况需要创建 Issue

以下内容应创建 Issue：

- 新功能
- Bug
- 重构
- 技术研究
- Unity 或 Package 升级
- 测试和发布任务
- 超过 30 分钟的明确工作

很小的文档修改、错别字修复和几分钟内可以完成的调整，可以直接提交，不必创建 Issue。

### 6.2 Issue 标题

标题应描述完成后的结果。

推荐：

- 玩家可以使用 WASD 八方向移动
- 玩家持有钥匙时可以打开房门
- 敌人发现玩家后进入追踪状态
- 修复玩家贴墙移动时的抖动

避免：

- 处理玩家代码
- 改一下 Door.cs
- 优化系统
- 研究 Unity

### 6.3 Issue 模板

```markdown
## 目标

描述这个任务完成后应该实现什么结果。

## 完成标准

- [ ] 条件一
- [ ] 条件二
- [ ] 条件三
- [ ] 在 Unity 编辑器中测试通过
- [ ] 必要时完成 Windows 构建测试

## 预计时间

2 小时

## 技术备注

记录预期使用的组件、脚本或实现限制。

## 不包含

明确本任务不处理的相关内容。
```

### 6.4 完成定义

Issue 只有满足以下条件才能关闭：

- 功能达到完成标准
- Unity Console 没有新增阻塞错误
- 已完成必要测试
- 代码已经提交
- Project 状态已经更新
- Clockify 已停止计时
- 必要的文档已经同步更新

## 7. 每次开发流程

### 7.1 开始开发前

1. 打开 GitHub Project
2. 检查当前里程碑
3. 从 Ready 中选择一个任务
4. 将任务移动到 In Progress
5. 确认任务完成标准
6. 启动 Clockify 计时
7. 根据任务规模决定是否创建分支

每次只选择一个主要任务。

### 7.2 开发过程中

- 只处理当前 Issue 范围内的内容
- 遇到新问题时先记录，不立即扩展范围
- 使用 AI 生成代码后必须阅读和测试
- 调试时间正常记录，不从开发耗时中排除
- 必要时进行小步提交

发现与任务无关的问题时：

1. 在当前 Issue 中记录
2. 必要时创建新的 Backlog Issue
3. 返回当前任务

### 7.3 开发结束前

1. 在 Unity 中运行当前功能
2. 检查 Console
3. 查看 `git status`
4. 检查是否包含无关修改
5. 提交代码
6. 停止 Clockify
7. 更新 Issue 或 Project 状态
8. 记录下一步动作

下一步应写成明确动作，例如：

> 在 Door 组件中读取 `PlayerInventory.HasKey`。

避免写成：

- 继续开发
- 继续研究
- 优化代码

## 8. 分支使用规范

### 8.1 可以直接提交到 main 的修改

- 文档错别字
- README 状态更新
- 注释调整
- 小型配置修改
- 15 分钟以内且风险很低的改动

直接提交前仍需确认 `main` 可以正常运行。

### 8.2 建议创建分支的修改

- 新增完整功能
- 修改多个脚本
- Bug 修复
- 系统重构
- 修改场景或 Prefab
- 增加 Unity Package
- 使用 AI 修改多个文件

### 8.3 必须创建分支的修改

- Unity 版本升级
- 渲染管线修改
- Input System 更换
- 大范围 Project Settings 修改
- 存档格式调整
- 场景结构重组
- 大规模重构
- 发布前整合修改

### 8.4 分支命名

格式：

```text
类型/Issue编号-简短描述
```

示例：

```text
feature/12-player-movement
fix/18-player-wall-jitter
refactor/23-interaction-system
chore/1-upgrade-unity-6-5
docs/7-project-guide
```

常用类型：

- `feature`：新功能
- `fix`：Bug 修复
- `refactor`：重构
- `chore`：升级、配置和维护
- `docs`：文档

---

## 9. Commit 规范

推荐格式：

```text
类型: 修改内容 (#Issue编号)
```

示例：

```text
feat: add player movement (#12)
fix: prevent repeated player damage (#18)
refactor: extract interaction interface (#23)
chore: upgrade project to Unity 6.5 (#1)
docs: add project development guide (#7)
```

常用类型：

- `feat`：新增功能
- `fix`：修复问题
- `refactor`：重构但不改变功能
- `docs`：文档
- `test`：测试
- `chore`：配置、依赖和维护
- `build`：构建相关
- `perf`：性能优化

不要使用含义模糊的提交信息，例如：

```text
update
fix
changes
修改代码
再改一下
```

一次提交应尽量只包含一类相关修改。

## 10. Pull Request 使用规范

PR 的主要作用是：

- 查看完整 Diff
- 检查是否包含无关修改
- 记录一组修改的目的
- 记录测试结果
- 关联并自动关闭 Issue
- 保持 main 分支稳定

### 10.1 建议使用 PR 的情况

- 一个完整功能
- 修改多个文件
- 修改场景或 Prefab
- Bug 调查和修复
- 系统重构
- 大量 AI 生成代码

### 10.2 必须使用 PR 的情况

- Unity 版本升级
- Package 大规模升级
- Project Settings 大范围变化
- 架构调整
- 高风险修改

### 10.3 PR 模板

```markdown
## 改动内容

- 修改内容一
- 修改内容二

## 测试结果

- [ ] Unity 项目可以正常打开
- [ ] Console 没有新增错误
- [ ] 相关功能测试通过
- [ ] 主要场景可以正常运行
- [ ] 必要时 Windows 构建成功

## 风险和注意事项

记录可能影响其他系统的内容。

## 关联 Issue

Closes #12
```

### 10.4 合并前检查

1. 查看 Files changed
2. 检查是否有无关文件
3. 检查 Unity 自动产生的序列化修改
4. 运行相关场景
5. 检查 Console
6. 确认 Issue 完成标准
7. 确认必要文档已经更新

普通功能默认使用 `Squash and merge`。

合并后删除已经完成的远程分支。

### 10.5 PR示例

假设 Issue 是：

```text
#1 升级此项目到 Unity 6.5
```
#### ◼️ 创建分支

```bash
git switch main
git pull
git switch -c chore/1-upgrade-unity-6-5
```

#### ◼️ 在新版本 Unity 中打开并升级

升级后检查：

```bash
git status
git diff --stat
```

然后提交：

```bash
git add .
git commit -m "chore: upgrade project to Unity 6.5 (#1)"
git push -u origin chore/1-upgrade-unity-6-5
```

#### ◼️ 在 GitHub 创建 PR

标题：

```text
升级项目到 Unity 6.5
```

描述可以使用：

```markdown
## 改动内容

- 将项目升级到 Unity 6.5
- 更新 Packages 配置
- 更新项目序列化文件

## 测试结果

- [√] 项目可以正常打开
- [√] Console 没有新增错误
- [√] 主要场景可以进入 Play Mode
- [√] 现有功能运行正常
- [√] Windows 构建成功

## 风险

升级修改了 ProjectSettings 和部分资源序列化内容。

Closes #1
```

#### ◼️ 自己审查

打开 Files changed，重点检查：

```text
Packages/manifest.json
Packages/packages-lock.json
ProjectSettings/
Assets 下被重新序列化的场景和 Prefab
```

确认没有莫名其妙的大量资源变化，再合并。

## 11. Clockify 时间记录

Clockify 只记录实际投入时间。

建议使用以下分类：

- Programming
- Design
- Art & Audio
- Testing
- Project Management

时间记录名称应关联 Issue：

```text
#12 玩家八方向移动
#18 修复玩家贴墙抖动
#23 重构交互系统
```

以下活动应计入实际时间：

- 编码
- Unity 编辑器操作
- 查阅技术资料
- 与 AI 讨论当前任务
- 调试
- 测试
- 构建
- 与项目直接相关的文档维护

休息或进行无关活动时暂停计时。

时间记录用于改进估算，不用于评价个人勤奋程度。

## 12. 每日开发节奏

工作日建议使用：

- 5 分钟：确认任务和完成标准
- 45～75 分钟：开发
- 10 分钟：测试、提交和记录

精力不足时使用最低开发流程：

1. 打开项目
2. 完成一个小修改
3. 运行测试
4. 提交代码
5. 记录下一步

保持项目上下文连续，比偶尔长时间突击更重要。

## 13. 每周规划

每周开始前安排一次 30～45 分钟的规划。

### 13.1 确定唯一周目标

每周只设置一个主要交付目标，例如：

> 玩家可以在灰盒地图中找到钥匙、打开房门并到达出口。

### 13.2 计算可用时间

计划容量以最近几周实际投入时间为基础。

计划任务不超过可用时间的 80%，其余时间用于：

- 调试
- 环境问题
- 返工
- 临时休息
- 估算误差

### 13.3 选择本周任务

将支持周目标的 Issue 从 Backlog 移到 Ready。

不要因为某个任务看起来有趣，就将它加入当前周计划。

## 14. 每周复盘

每周结束后，在 `docs/weekly/` 中创建复盘文件。

命名格式：

```text
YYYY-Www.md
```

例如：

```text
2026-W31.md
```

复盘模板：

```markdown
# 2026 W31 周复盘

## 本周目标

描述本周计划完成的主要交付。

## 实际完成

- [√] 已完成事项
- [ ] 未完成事项

## 时间统计

- 计划投入：
- 实际投入：
- Programming：
- Design：
- Art & Audio：
- Testing：
- Project Management：

## 本周交付

描述现在实际可以运行或体验的内容。

## 计划偏差

哪些任务的预计时间与实际时间差距较大。

## 原因分析

记录造成偏差的具体原因。

## 做得好的地方

记录应该保留的工作方式。

## 主要问题

记录本周最大的阻碍。

## 下周调整

只选择一到两个流程调整。

## 下周目标

描述下周唯一主要目标。

## 下周第一个任务

写出下次开发可以直接执行的动作。
```

复盘重点回答：

1. 本周真正交付了什么
2. 实际投入了多少时间
3. 哪项估算偏差最大
4. 什么阻碍了进度
5. 下周准备改变什么

## 15. 文档维护规范

项目文档存放在 `docs/`。

建议逐步建立：

```text
docs/
├── PROJECT_GUIDE.md
├── DESIGN.md
├── ROADMAP.md
├── ARCHITECTURE.md
├── weekly/
└── decisions/
```

各文档职责：

- `PROJECT_GUIDE.md`：记录项目的开发和维护流程
- `DESIGN.md`：记录核心玩法、玩家体验、项目范围和明确不做的内容
- `ROADMAP.md`：记录阶段目标和里程碑，不记录具体任务状态
- `ARCHITECTURE.md`：记录主要系统职责、数据流和技术约定
- `weekly/`：记录每周计划和复盘
- `decisions/`：记录重要且长期有效的技术决策

只有当项目出现多个稳定系统后，才需要创建 `ARCHITECTURE.md`。

### 15.1 文档更新原则

以下情况需要更新文档：

- 项目范围发生变化
- 核心玩法发生变化
- 开发流程发生变化
- Unity 版本或运行方式发生变化
- 系统结构发生重要变化
- 做出会长期影响项目的技术决策

以下内容通常不需要进入长期文档：

- 临时调试过程
- 单个 Bug 的调查记录
- 某次任务的具体进度
- 可以直接从代码中看懂的实现细节

临时内容应记录在对应 Issue 中。

文档应与相关代码放在同一个提交或 PR 中更新。

## 16. 里程碑完成标准

完成一个里程碑时，应执行：

1. 检查对应 Issue 是否全部处理
2. 完成一次完整流程测试
3. 生成 Windows 测试构建
4. 修复阻塞流程的 Bug
5. 更新 README 和 Roadmap
6. 关闭 GitHub Milestone
7. 创建 Git Tag 或 GitHub Release
8. 保存可运行的构建版本
9. 记录本阶段复盘
10. 明确下一个里程碑目标

---

## 17. 当前开发纪律

本项目遵循以下规则：

- 每周只有一个主要目标
- 每天只有一个必须完成的任务
- In Progress 同时最多一个任务
- 单个任务预计不超过 4 小时
- 计划不超过可用时间的 80%
- 每次开发结束必须提交并记录下一步
- 高风险修改必须使用独立分支和 PR
- 实际耗时统一记录在 Clockify
- 每周复盘只调整一到两个问题

当流程本身开始明显占用开发时间时，应优先简化流程。
